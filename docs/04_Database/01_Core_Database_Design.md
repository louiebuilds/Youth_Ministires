# Core Database Design

**Document ID:** DB-001  
**Version:** v0.4.0  
**Status:** Complete  
**Milestone:** 3 — Core Database Foundation  
**Date:** 2026-07-23

---

## Purpose

This document defines the first version-controlled PostgreSQL schema for the
Youth Ministries Platform. It translates the approved person-centric domain
model and the Milestone 2 account-role decision into a database foundation.

Milestone 3 establishes only the shared records required by later feature
milestones. It does not implement feature workflows.

---

## Milestone Scope

The core schema includes:

- authenticated account profiles;
- one permanent primary role per account;
- people and separate account contexts;
- households;
- household memberships;
- students and one required primary household;
- adult-to-student relationships and operational permissions;
- events;
- temporary event-scoped volunteer assignments;
- append-only audit events;
- update-timestamp support;
- indexes, constraints, and baseline Row-Level Security.

The following remain outside Milestone 3:

- final permission matrix and relationship-aware access policies;
- student, family, event, or volunteer application screens;
- attendance and check-in/check-out records;
- event registrations and waitlists;
- permission-form templates and submissions;
- communication delivery records;
- reporting projections;
- file-storage buckets and policies;
- production retention schedules.

Those items require their approved feature or security milestones.

## Design Principles

### Stable identifiers

Application records use UUID primary keys generated by PostgreSQL.

### UTC timestamps

Operational timestamps use `timestamp with time zone` and default to
`now()`. PostgreSQL stores these values as absolute points in time.

### Archive before delete

Core ministry records use lifecycle status fields and archive timestamps.
Application workflows must archive rather than permanently delete these
records.

### Deny by default

Row-Level Security is enabled and forced on protected tables. No broad
authenticated-user data policies are created in this milestone. The later
security milestone must add narrowly scoped policies after the permission
matrix is approved.

### Database invariants

Rules that must always be true are enforced with foreign keys, unique
constraints, check constraints, and controlled triggers rather than relying
only on application code.

## Enumerations

### `account_role`

Permanent account roles:

- `platform_administrator`
- `youth_pastor`
- `staff_member`
- `volunteer`
- `parent`

Each profile has exactly one role. Temporary volunteer service is represented
by an event assignment and never changes this value.

### `account_status`

- `invited`
- `active`
- `suspended`
- `disabled`
- `archived`

### `person_status`

- `active`
- `inactive`
- `archived`

### `household_status`

- `prospect`
- `active`
- `inactive`
- `archived`

### `student_status`

- `prospective`

- `active`

- `archived`

## Tables

### `profiles`

Provides application account data for a Supabase Auth identity.

| Column | Purpose |
|---|---|
| `id` | Primary key and foreign key to `auth.users.id` |
| `person_id` | Optional link to the represented person |
| `primary_role` | One permanent role |
| `status` | Account lifecycle |
| `display_name` | Safe application display name |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

More than one profile may link to the same person. This supports separate
personal and administrative accounts without duplicating the person.

### `people`

Stores each real-world individual once.

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `first_name` | Legal or commonly used first name |
| `preferred_name` | Optional preferred name |
| `last_name` | Last name |
| `email` | Optional normalized contact email |
| `phone` | Optional contact phone |
| `status` | Person lifecycle |
| `archived_at` | Archive timestamp when applicable |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

This milestone does not attempt fuzzy duplicate detection. Exact account email
uniqueness remains enforced by Supabase Auth.

### `households`

Stores the internal household entity displayed to users as a family.

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `name` | Household display name |
| `status` | Household lifecycle |
| `address_line_1` | Optional mailing address |
| `address_line_2` | Optional secondary address |
| `city` | Optional city |
| `region` | Optional state or region |
| `postal_code` | Optional postal code |
| `country_code` | ISO-style two-character country code |
| `archived_at` | Archive timestamp when applicable |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

### `household_memberships`

Connects people to households without duplicating person records.

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `household_id` | Related household |
| `person_id` | Related person |
| `relationship_label` | Ministry-friendly relationship text |
| `is_responsible_adult` | Identifies a responsible adult |
| `is_primary_contact` | Identifies a primary household contact |
| `receive_email` | Email preference |
| `receive_sms` | SMS preference |
| `receive_emergency_notifications` | Emergency preference |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

A person may belong to more than one household when future custody or family
arrangements require it. The same person may appear only once in a given
household.

### `students`

Stores student-specific data separately from the underlying person.

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `person_id` | Unique person represented by the student |
| `primary_household_id` | Required primary household |
| `birth_date` | Required date of birth |
| `grade` | Required ministry grade label |
| `status` | Student lifecycle |
| `medical_summary` | Restricted operational medical summary |
| `allergy_summary` | Restricted allergy summary |
| `dietary_summary` | Restricted dietary summary |
| `archived_at` | Archive timestamp when applicable |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

Medical fields are included because they are part of the approved student
domain, but baseline RLS exposes them to no authenticated client. Final
need-to-know access belongs to the security milestone.

### `student_relationships`

Connects an adult or other person to a student and records the permissions
attached to that relationship.

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `student_id` | Related student |
| `person_id` | Related person |
| `relationship_type` | Ministry relationship label |
| `is_legal_guardian` | Guardian indicator |
| `is_emergency_contact` | Emergency contact permission |
| `is_authorized_pickup` | Pickup permission |
| `may_sign_permission_forms` | Form-signing permission |
| `may_view_student_information` | Future portal-view permission |
| `receive_email` | Relationship-specific email preference |
| `receive_sms` | Relationship-specific SMS preference |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

The same person may have only one relationship record per student. Multiple
permissions can be true on that record.

### `events`

Provides the shared event identity required by scoped assignments and future
event feature tables.

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `name` | Event name |
| `event_type` | Configurable ministry event type text |
| `status` | Event lifecycle |
| `starts_at` | Scheduled start |
| `ends_at` | Scheduled end |
| `timezone` | IANA ministry timezone |
| `capacity` | Optional non-negative capacity |
| `archived_at` | Archive timestamp when applicable |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

The database requires an end time after the start time.

### `event_volunteer_assignments`

Grants temporary operational context for a single event.

| Column | Purpose |
|---|---|
| `id` | Primary key |
| `event_id` | Assigned event |
| `profile_id` | Assigned authenticated account |
| `assignment_role` | Event responsibility |
| `status` | Assignment lifecycle |
| `starts_at` | Optional narrower assignment start |
| `ends_at` | Optional narrower assignment end |
| `assigned_by_profile_id` | Account that made the assignment |
| `created_at` | Creation timestamp |
| `updated_at` | Last update timestamp |

An assignment does not modify `profiles.primary_role`. A profile may hold only
one instance of the same assignment role for an event.

### `audit_events`

Stores append-only accountability records.

| Column | Purpose |
|---|---|
| `id` | Ordered identity primary key |
| `event_id` | Public UUID event identifier |
| `occurred_at` | Event timestamp |
| `actor_profile_id` | Acting profile when known |
| `action` | Stable action name |
| `entity_type` | Affected entity category |
| `entity_id` | Affected UUID when applicable |
| `result` | `success`, `failure`, or `denied` |
| `source` | `web`, `api`, `system`, or `migration` |
| `request_id` | Optional request correlation identifier |
| `metadata` | Approved non-secret JSON context |

Ordinary authenticated and anonymous roles receive no direct insert, update,
or delete policy. Later services will write through a narrowly controlled
server or database function after the security design is approved.

## Integrity Rules

- Every profile references exactly one Supabase Auth user.
- Every profile contains exactly one permanent primary role.
- Multiple profiles may reference the same person.
- Every student references exactly one person and one primary household.
- One person may have at most one student profile.
- A person appears at most once in a household.
- A person has at most one relationship record with a student.
- Event end time must be later than event start time.
- Assignment end time must be later than assignment start time.
- Archive timestamps must agree with archived lifecycle states.
- Audit rows cannot be updated or deleted by application roles.

---

## Row-Level Security Baseline

Milestone 3 applies a safe baseline:

- RLS is enabled and forced on every application table.
- Authenticated users may read only their own profile row.
- No authenticated user can assign or change their own role.
- No broad policies expose people, households, students, relationships,
  events, assignments, or audit data.
- The PostgreSQL ownership or Supabase service role remains reserved for
  controlled administration and future server workflows.

This baseline intentionally makes the schema safer than the future user
experience requires. The approved security milestone must expand access with
tested, resource-specific policies.

## Migration Strategy

The schema is introduced by:

```text
supabase/migrations/202607230001_core_database_foundation.sql
```

The migration is additive. It does not remove or alter existing application
data. It can be applied to a clean Supabase project and is designed to fail
clearly if conflicting objects already exist.

## Verification Requirements

Milestone 3 verification must demonstrate:

- SQL parses and applies successfully to the connected Supabase project;
- all expected types, tables, constraints, indexes, triggers, and policies
  exist;
- a new Auth user receives one `parent` profile by default;
- an authenticated account can read its own profile but not another profile;
- an authenticated account cannot change its own permanent role;
- person, household, student, event, assignment, and audit tables deny direct
  access without an explicit policy;
- event-scoped assignments do not change the permanent account role;
- generated TypeScript database types compile;
- lint and the production application build pass;
- Product Owner acceptance testing passes.
